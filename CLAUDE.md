# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

All commands run from the repo root (`DocViewer.sln`) or from `src/DocViewer.Web/`.

```bash
dotnet build                            # build the solution
dotnet run --project src/DocViewer.Web  # run locally (port from Properties/launchSettings.json)
```

There is no test project yet.

**Do not run `dotnet clean` / delete `obj`+`bin` and rebuild without first stripping the macOS `com.apple.provenance` xattr from `wwwroot/**`** (`find wwwroot -type f -exec xattr -d com.apple.provenance {} \; 2>/dev/null`). On this SDK (9.0.300) that xattr makes the StaticWebAssets MSBuild task throw `Last write time for '...' is not defined`, which is why `StaticWebAssetsEnabled` is set to `false` in the `.csproj` and `Program.cs` uses classic `app.UseStaticFiles()` instead of `app.MapStaticAssets()`. If a future SDK upgrade fixes the underlying bug, this workaround (and the corresponding `@RenderSectionAsync("Styles")` plumbing in `_Layout.cshtml` used to pull in per-view CSS without asset bundling) can likely be removed.

**`SixLabors.ImageSharp` is pinned to 3.1.12, not the latest 4.x** — v4 requires a paid Six Labors license at build time (`No Six Labors license found`); 3.x is still under the free split license. Don't bump this major version without checking licensing first.

## Architecture

Single ASP.NET Core MVC project (`net9.0`) that converts anything that isn't already a PDF into one, then renders it in-browser via PDF.js. No server-side dependency beyond the initial upload/convert step, other than an external LibreOffice install for Office formats.

**Flow:** `HomeController.Upload` (multipart form) or `HomeController.Index(file:)` (dev-only `?file=` query shortcut, see below) accepts a document → non-PDF files go through `IDocumentConverter` → resulting PDF bytes are handed to `IDocumentStore.Save`, which returns an opaque `Guid` → redirect to `/Viewer/{id}`.

- **`IDocumentStore` / `DocumentStore`** — in-memory `ConcurrentDictionary<Guid, DocumentRecord>` (singleton). The browser never sees a real file path or name, only the `Guid`. Normal removal: `wwwroot/js/viewer.js` fires `navigator.sendBeacon` to `POST /Viewer/{id}/release` on the `pagehide` event, so the converted PDF drops out of memory once the user is actually done with the viewer. `Remove()` does *not* delete outright, though - it starts a 15-second grace window (`DocumentRecord.ReleaseRequestedAt`). Pressing refresh fires the exact same `pagehide` event as closing the tab, so the beacon alone can't tell them apart; if the reloaded page's own request for the same document (`Viewer/Index` or the stream fetch) lands within that window, `Get()` treats it as "still in use" and cancels the release - only if nothing asks for it in time does `EvictExpired` actually remove it. The 30-minute TTL (evicted lazily on save/get) is a second, longer fallback for when even the grace window is missed (tab/browser killed, crash). Swap for a distributed cache (e.g. Redis) if this needs to run behind more than one instance.
- **`IDocumentConverter` / `DocumentConverter`** — dispatches by extension to one of three conversion paths, all producing PDF bytes:
  - `.eml` (MimeKit) / `.msg` (MsgReader's `Storage.Message`) → a header block (From/To/Cc/Subject/Date) + body HTML, resolving `cid:` inline images to base64 data URIs for `.eml`, then print-to-PDF via headless Chromium (PuppeteerSharp).
  - `.txt` / images (`.jpg`/`.jpeg`/`.png`/`.gif`/`.bmp`/`.webp`) → a minimal HTML wrapper, also print-to-PDF via headless Chromium. Images use `SixLabors.ImageSharp` to read native pixel dimensions and set an `@page` size to match (with `PdfOptions.PreferCSSPageSize = true`), so the PDF page is exactly the image's size with no letterboxing.
  - Office formats (`.docx`/`.xlsx`/`.doc`/`.xls`/`.pptx`/`.ppt`/`.odt`/`.ods`) → shells out to LibreOffice headless (`soffice --headless --convert-to pdf`) rather than re-deriving layout by hand. For `.xlsx`/`.xls` specifically, `FitSpreadsheetToPageWidthAsync` first loads the workbook via NPOI (`XSSFWorkbook`/`HSSFWorkbook`) and forces `FitToPage`/`PrintSetup.FitWidth=1`/`FitHeight=0`/`Landscape=true` on every sheet before handing it to LibreOffice — without this, LibreOffice honors whatever print setup (or lack of one) is stored in the file and tiles wide sheets across multiple pages column-wise, unlike Excel's own on-screen view which never paginates horizontally. `AcceptNPOIOSMFLicense=true` is set in the `.csproj` to silence NPOI's OSMF license-acceptance build warning.
  - **Concurrency**: the headless Chromium browser is a lazily-launched *singleton* (`GetBrowserAsync`, guarded by a semaphore) reused across all HTML-based conversions — each request gets its own `Page` (isolated), not its own browser *process*. Every LibreOffice conversion gets a brand-new temp working directory *and* a brand-new `-env:UserInstallation` profile directory (`ConvertOfficeDocumentAsync`) — concurrent `soffice` invocations sharing a profile directory contend for the same lock file and fail outright, so isolation here isn't optional. Both were verified under real concurrent load (mixed same-file/different-file, same-format/different-format bursts) before being considered done.
- **`ViewerController`** — `Index` renders the toolbar shell for a given document id; `Stream` serves the raw PDF bytes for `pdf.js` to fetch. The stream endpoint sets `Cache-Control: no-store`, `Content-Disposition: inline` with no filename, and `X-Content-Type-Options: nosniff` — this is a deliberate part of the "no download" requirement, not incidental.
- **`HomeController.Index(string? file)`** — lets a caller open `http://host/?file=<absolute-path>` to skip the upload form, unconditionally in every environment including Production, by explicit instruction. A bare query string naming an arbitrary server-side file path is a classic local-file-read vulnerability with no allowlist or key gating it here - an earlier revision required a `LocalFileAccess:SharedKey` shared secret outside `Development`, but that was deliberately removed on request. This is only appropriate because the deployment is intranet-only; don't assume that tradeoff holds for a different deployment without checking first.
- **`wwwroot/js/viewer.js`** — loads `pdf.js` as an ES module (`wwwroot/lib/pdfjs/pdf.mjs` + `pdf.worker.mjs`, vendored directly from a pdf.js release zip, not npm/libman), fetches the PDF via `fetch()` (not a direct `<a>`/`<embed>` link) into an `ArrayBuffer`, and renders each page to its own `<canvas>` + text layer + link layer in a continuously-scrollable stack (not single-page-swap). All toolbar chrome (zoom, rotate, page nav, first/last, thumbnail sidebar) is hand-built here — this intentionally does *not* use pdf.js's bundled `viewer.html`, because that ships its own download/print/open-file buttons that would have to be hidden/patched instead of simply not existing. Also handles: encrypted-PDF password prompting via `loadingTask.onPassword` (must be set as a property on the returned loading task, *not* passed inside the `getDocument({...})` options object — pdf.js silently ignores it there), auto-linking plain-text URLs the source didn't mark as real link annotations (rendered-position adjacency, not raw text concatenation, decides whether two text runs are one continuous token — see inline comments before changing; this logic has a documented history of both under- and over-matching bugs), a loading overlay shown until the first full render completes (hidden/re-shown around the password prompt too, so the two don't visually compete), and in-document search (see below).
- **Search** (`viewer.js`, "Search" section) — finds matches directly against the same rendered text-layer `<span>` elements `linkifyTextLayer` already reads (`buildPageSearchIndex`), so results can never drift from what's on screen; there's no separate server-fetched text index. A page's flat text + span offsets get rebuilt on every text-layer re-render (zoom/rotate rebuilds every span from scratch), but the matches themselves (page + character range) stay valid across that, since only *which DOM nodes* an offset maps to changes, not the underlying PDF text. Highlighting uses `Range.setStart`/`setEnd` (via `nodePositionAtOffset`, which walks into the correct text node since linkify may have split a span's text across a plain-text node + an `<a>`) and `getClientRects()` to draw boxes in a `.search-highlight-layer` sitting between the canvas and the (transparent) text layer — not by mutating span text content, which would risk clobbering the linkify-inserted `<a>` tags. Opens via the toolbar button or Ctrl/Cmd+F (default browser find is suppressed).
- **`wwwroot/js/protect.js`** — best-effort UX deterrents (blocks right-click, drag, copy, and Ctrl+S/P/U/C everywhere; blocks text *selection* everywhere **except** inside the PDF text layer, where highlighting is intentionally allowed). The password-prompt dialog (`.password-dialog`) is explicitly exempted from all of these — it's a normal input field, not document content. This is explicitly not real DRM: PDF bytes are reachable via dev tools/network tab by design, since the requirement was UX-level protection, not encryption.
- **`.mjs` content type** — `Program.cs` registers `.mjs` → `text/javascript` on a custom `FileExtensionContentTypeProvider` because the default provider doesn't map it, and browsers refuse to execute an ES module served with the wrong MIME type.
- **`Encoding.RegisterProvider(CodePagesEncodingProvider.Instance)`** in `Program.cs` — required for MsgReader to decode legacy header codepages (Windows-874/Thai, etc.); without it, any `.msg` with a non-ASCII-encoded header throws `NotSupportedException` at parse time. .NET Core doesn't register these by default.
- **Windows/IIS support** — `FindSofficeExecutable` includes Windows install paths, and the LibreOffice `-env:UserInstallation` profile path is built with `new Uri(profileDir).AbsoluteUri` rather than raw string interpolation, because `file://` + a Windows path (`C:\...`) is not a valid file URI and LibreOffice would silently fail to apply the per-request profile isolation. `src/DocViewer.Web/web.config` is the publish template IIS uses (`dotnet publish` fills in `%LAUNCHER_PATH%`/`%LAUNCHER_ARGS%`) — it raises IIS's own `requestFiltering` upload cap to 500 MB and maps `.mjs` to `text/javascript`, both of which sit in front of the app (IIS's own modules, not ASP.NET Core's) and would otherwise reject/mis-serve requests regardless of what `HomeController`'s `[RequestSizeLimit]` or `Program.cs`'s `FileExtensionContentTypeProvider` allow.

Views follow standard MVC conventions (`Views/{Controller}/{Action}.cshtml`) with one exception: `Viewer/Index.cshtml` injects its own stylesheet via a `Styles` section (`@await RenderSectionAsync("Styles", ...)` was added to `_Layout.cshtml` for this) since the project has no bundler.
